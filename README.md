# Pangea

Текстовая RPG для ВКонтакте на Scala + ZIO.

## Требования

- Docker и Docker Compose

## Деплой на VDS

### 1. Установить Docker

```bash
curl -fsSL https://get.docker.com | sh
```

### 2. Склонировать репозиторий

```bash
git clone <repo_url> /opt/pangea
cd /opt/pangea
```

### 3. Создать файл с секретами

```bash
cp .env.example .env
nano .env
```

Заполнить:

```env
POSTGRES_DB=pangea
POSTGRES_USER=pangea
POSTGRES_PASSWORD=your_strong_password

VK_TOKEN=your_vk_token_here

# Пароль админ-панели («/admin» в личке бота) и выдачи логов по HTTP.
# Пусто — и панель, и `GET /logs` закрыты для всех.
ADMIN_PASSWORD=
```

### 4. Зеркала Docker Hub

С российских серверов Docker Hub периодически пропадает целиком — и тогда не
собрать даже бота: базовый образ `eclipse-temurin` берётся оттуда. Поэтому один
раз на сервере прописываем зеркала (Google и Timeweb); Docker перебирает их сам,
Docker Hub — последним:

```bash
sudo sh docker/registry-mirrors.sh
```

Скрипт сохраняет остальные настройки `/etc/docker/daemon.json` и перечитывает
конфиг без перезапуска контейнеров. Свои зеркала — аргументами.

### 5. Запустить

```bash
docker compose up -d --build
```

При первом запуске Docker соберёт образ (~5 минут), поднимет PostgreSQL и прогонит все миграции автоматически.

### 6. Проверить

```bash
docker compose ps        # все сервисы должны быть Up
docker compose logs -f app        # логи бота
docker compose logs -f collector  # приём событий ВК
```

## Обновление

Всё — на сервере, в каталоге проекта (тот, куда склонирован репозиторий).
Сервер берёт код только из `master`: сначала коммит и пуш, потом выкладка.
Что именно выкладывать — зависит от того, что поменялось:

| Что поменялось | Что делать |
|---|---|
| Игра, бот — почти всегда | `scripts/deploy-bot.sh` |
| Приём событий ВК: `VkIngest`, `VkLongPoll`, `Role`, `entrypoint.sh`, настройки `collector` | бот, затем сборщик (см. ниже) |
| VK Mini App (`web/`) | `scripts/deploy-app.sh` |
| `docker/caddy/Caddyfile` | `docker compose restart caddy` |
| `docker/prometheus/prometheus.yml` | `docker compose restart prometheus` |
| Дашборд Grafana | ничего: Grafana сама перечитывает папку раз в 10 с |
| `scripts/` (бэкапы и т. п.) | `git pull --ff-only` |

### Бот — новая версия игры

```bash
scripts/deploy-bot.sh
```

Скрипт выкладывает бота без паузы в ходах — новый поднимается рядом со
старым:

1. `git pull --ff-only` — свежий `master`. Своих правок на сервере быть не должно,
   иначе pull (и скрипт) остановится.
2. `docker compose build app` — сборка образа, 2–3 минуты. Старый бот всё это
   время работает.
3. Новый бот — рядом со старым (`--scale app=2`). При старте он катит миграции —
   пока старый ещё работает, поэтому схема только расширяется (`CLAUDE.md`).
4. Ждёт, пока новый ответит на `GET /health` (healthcheck в docker-compose):
   обычно ~10 секунд, не дольше 5 минут. Не поднялся — скрипт гасит новый,
   печатает его лог и выходит с ошибкой; **старый работает дальше**, игра не
   стоит.
5. Гасит старый (`docker stop -t 30`): тот перестаёт брать новые события,
   доделывает начатые ходы, отпускает ведущего и локи. Скрипт печатает, как он
   остановился, и сохраняет его лог за 5 минут в `/var/log/pangea-deploy/`.
6. Удаляет старый контейнер; остаётся один бот.
7. Чистит кэш сборки от слоёв прошлых сборок — копий `app.jar`,
   `sbt app/assembly`, исходников: каждая сборка оставляет ~290 МБ; а после
   смены зависимостей или базового образа — и прежних `apt-get` и `sbt update`.
   Базовые образы и всё, чем пользовалась последняя сборка, остаются; кэш
   держится около 1,5–2 ГБ (`docker builder du`).

Вся выкладка — 3–4 минуты. Пример вывода:

```
17:41:31 Поднимаю новый бот рядом со старым (pangea-app-2)
17:41:32 Жду, пока новый (pangea-app-3) будет готов
17:41:42 Новый готов. Гашу старый: доделает начатые ходы и выйдет
17:42:12 Старый не вышел сам за 30 с — Docker его добил (exit 137). Как шла остановка:
...  Остановка: фон остановлен
Лог старого за 5 минут: /var/log/pangea-deploy/pangea-app-2-2026-11-04_174212.log
17:42:12 Готово: pangea-app-3 — Up 41 seconds (healthy)
```

**`exit 137` у старого бота — известное и безвредное.** Сама остановка
занимает секунду: фон останавливается, ходы доделаны, ведущий и пулы
соединений отпущены (видно в его логе). Дальше пустой процесс висит на выходе
из ZIO, и через 30 секунд Docker его добивает — делать ему к этому времени
нечего. Так было и до выкладки «рядом»; это лишь лишние 30 секунд.

Номер контейнера бота меняется от выкладки к выкладке (`pangea-app-2`, `-3`, …)
— это нормально: `docker compose ps app` и `docker compose logs app` видят
всех ботов, Prometheus находит их по имени сервиса.

#### Проверить после выкладки

- `docker compose ps` — бот один и `healthy`;
- `docker compose logs --since 5m app | grep -E "goose|ERROR"` — миграции прошли
  (`successfully migrated` или `no migrations to run`), ошибок нет (кроме
  `NoMorePlaceForItems` — это переполненная сумка игрока, а не поломка);
- Grafana: «Очередь ВК — ждут» около нуля, «Ведущий бот» — единица у одного
  бота, «Локи игроков — соединения» — `pending` 0.

#### Откатить

Скрипт всегда берёт `master`, поэтому откат — тоже через git: `git revert <хеш>`
в `master`, пуш, затем `scripts/deploy-bot.sh`. Схема базы при этом не
откатывается и не должна: она только расширялась, прошлый код с ней работает.

#### Чего не делать

- `docker compose up -d --build` без имени сервиса, `docker compose up -d app`,
  `docker compose restart app` — пересоздают бота разом, с паузой в ходах, а
  первая ещё и задевает сборщика и caddy;
- миграции, ломающие схему (переименование, удаление колонок разом): новый бот
  катит их, пока старый ещё работает, — см. `CLAUDE.md`.

#### Как двое уживаются

Пока новый и старый бот работают вместе (секунды), их разводит Postgres:

- **лок игрока** — advisory-лок по id игрока (`PlayerLock`, `AdvisoryLocks`):
  ход, таймер, посылка, выплата одного игрока идут по одному и между ботами.
  Держится на своём соединении из отдельного пула, пока идёт ход; бот упал —
  Postgres отпускает его локи сам. Размер пула — `POSTGRES_LOCK_POOL_SIZE`
  (20), занятость — график «Локи игроков — соединения»: `pending` > 0 — ходы
  ждут соединения, пул пора поднять (следя, чтобы двум ботам с основными
  пулами и сборщику хватало `max_connections` Postgres — 100);
- **ведущий** — advisory-лок одного бота (`Leader`): только он делает одиночные
  фоновые дела — сверку платежей, оплату билетов, обход почты, уборку очереди.
  Старый отпускает его в самом конце остановки, новый подхватывает за секунды
  (график «Ведущий бот»);
- **очередь ВК и таймеры** — захват через `FOR UPDATE SKIP LOCKED`: событие или
  задачу берёт один бот.

### Сборщик — приём событий ВК

Только если менялся сам приём (см. таблицу). Образ у сборщика общий с ботом,
поэтому сначала выкладывается бот — он собирает образ, — затем пересоздаётся
сборщик:

```bash
scripts/deploy-bot.sh
docker compose up -d --no-deps collector
```

Пока сборщик перезапускается (около 10 секунд), caddy держит колбэк ВК до 10
секунд, а Long Poll после старта продолжает с сохранённого места: сообщения не
теряются, бот тем временем разбирает то, что уже в очереди.

### VK Mini App и caddy

Новая версия приложения (`web/`) — пересборка caddy, и только его:

```bash
scripts/deploy-app.sh
```

Внутри — `git pull --ff-only` и `docker compose up -d --build --no-deps caddy`.
`scripts/deploy-bot.sh` приложение не обновляет: оно собирается в образе caddy.
Приложение зовёт новые запросы бота — сначала бот, потом приложение.

Только Caddyfile — `git pull --ff-only` и `docker compose restart caddy`
(перезапуск, а не `caddy reload`: файл смонтирован в контейнер по одному, и
после pull контейнер может видеть его старым). В обоих случаях caddy
недоступен несколько секунд: колбэк ВК и уведомления кассы в эти секунды
повторят сами ВК и касса.

## Роли: сборщик и бот

Образ один, роль — переменная `ROLE`:

- `collector` — сборщик: колбэк ВК (`POST /`) и Long Poll кладут события в
  очередь `vk_inbox`, и всё. Миграций не катит, игры не знает. Выкладывается
  редко — пока выкатывают бота, ВК отвечает он, и ни одно сообщение не
  теряется: они ждут в очереди;
- `bot` — бот: разбор очереди (ходы), таймеры, фоновые циклы, касса, Mini App,
  логи. Их может быть два разом — так выкладывает `scripts/deploy-bot.sh`;
- `all` — всё в одном процессе (по умолчанию; удобно локально).

Наружу смотрит только `caddy` (порты 80 и 443, `docker/caddy/Caddyfile`): по
HTTP колбэк ВК идёт сборщику, `/pay`, `/api`, `/logs` — боту; по HTTPS — Mini
App и те же маршруты бота. Пока бот или сборщик перезапускается, запрос ждёт
его до 10 секунд, а не получает ошибку. Prometheus читает метрики обоих:
доставку от ВК пишет сборщик, всё остальное — бот.

## Локальная разработка

Для запуска тестов PostgreSQL не нужен — тесты используют in-memory заглушки.

```bash
sbt core/test
```

Для локального запуска бота нужно поднять PostgreSQL (например, через `docker compose up postgres -d`) и задать переменные окружения:

```bash
export POSTGRES_JDBC_URL=jdbc:postgresql://localhost:5432/pangea
export POSTGRES_USER=pangea
export POSTGRES_PASSWORD=pangea
export VK_TOKEN=your_token
sbt app/run
```

## Архитектура

```
app/          — точка входа, HTTP-сервер (VK Callback API)
core/         — игровая логика, модели, состояния, DAO
migrations/   — SQL-миграции (goose)
web/          — VK Mini App: инвентарь и аукцион (React + TypeScript)
```

Бот работает как конечный автомат: каждый игрок находится в одном из состояний (`Registration`, `Dungeon`, `HeroStats`, ...), которое хранится в БД. При получении события от VK вызывается обработчик текущего состояния.

## Донат (покупка дублонов)

Продажа дублонов за рубли через интернет-эквайринг Т-Банка. Вход — Торговый дом
на Торговой площади, банкир Рахадим → «Купить дублоны».

Пока `TBANK_TERMINAL_KEY` и `TBANK_PASSWORD` пусты, донат выключен: экран у
Рахадима остаётся заглушкой, заказы не создаются. Так же он выключится сам, если
прайс-лист не пройдёт проверку при запуске — в логах будет строка с причиной.

Что нужно, чтобы включить:

1. Заполнить в `.env` переменные `TBANK_*` (см. `.env.example`).
2. Поправить прайс-лист в блоке `tbank.packs` файла `app/src/main/resources/application.conf`.
   Цены там в **копейках** — ровно в таком виде их ждёт банк.
3. Поднять HTTPS перед приложением и указать вебхук
   `https://<домен>/pay/tbank/notify` в `TBANK_NOTIFICATION_URL`. Сейчас
   приложение слушает голый HTTP, так что нужен обратный прокси с сертификатом.
4. В настройках терминала (или теми же переменными) задать `SuccessURL` и
   `FailURL` — они ведут прямо в диалог с сообществом.

### Сертификат кассы

`securepay.tinkoff.ru` отдаёт сертификат, подписанный корневым CA Минцифры
(«Russian Trusted Root CA»), которого нет ни в стандартных хранилищах ОС, ни в
`cacerts` JVM. Без него первый же запрос к кассе падает на PKIX
(«unable to find valid certification path»), то есть донат не работает вовсе.

Корневой сертификат лежит в `docker/russian_trusted_root_ca.cer` и добавляется
в хранилище JVM при сборке образа, с проверкой отпечатка. Если запускаешь бота
не через Docker — добавь его в `cacerts` сам:

```bash
keytool -importcert -trustcacerts -cacerts -storepass changeit \
  -alias russian-trusted-root-ca -file docker/russian_trusted_root_ca.cer
```

### Как идёт выдача

Выдача дублонов идёт **только** по нотификации банка со статусом `CONFIRMED`, и
ровно один раз: `CONFIRMED` приходит минимум дважды, а кнопка «Проверить оплату»
и фоновая сверка тянут за ту же ручку. Страницы `SuccessURL`/`FailURL` ничего не
начисляют — игрок может открыть их руками.

## Билеты за активность в группе

Лайк свежего поста группы — золотой билет, по одному на пост. Комментарий под
свежим постом — серебряный билет, по одному в сутки (московские, с полуночи).
Свежий — вышедший не раньше суток назад; билеты идут только игрокам с героем.
О каждом новом билете игроку сразу приходит письмо: шуточная находка (одна из
десяти) и счёт билетов за неделю. Неделя — с понедельника 00:00 по Москве; в начале новой недели каждый золотой
билет прошлой оборачивается 🟡 2, каждый серебряный — 🪙 от 100 до 300, у
каждого билета своя сумма (с ближайшим
действием, где бы ни были). Игроку — одно письмо с итогом, в общую беседу —
сколько роздано всего.

Что нужно, чтобы билеты заработали (Управление → Работа с API → Callback API):

1. **Типы событий:** включить «Запись на стене: добавление», «Комментарий на
   стене: добавление» и «Отметка «Мне нравится»: добавление».
2. **Секретный ключ:** придумать и вписать тот же в `.env` как `VK_SECRET`.
   Без ключа события группы не принимаются: их легко подделать.
3. Версия API для Callback — не ниже 5.103 (в ней появились события лайков).

Посты, вышедшие до включения, бот не знает: за них очков нет.

## Код друга

В «Персонаже» → «🎟 Код друга» игрок видит свой код (восемь цифр) и, пока его
герой не выше 5 уровня и код он ещё не вписывал, может вписать чужой. Вписал —
Азат благословляет его на 3 дня, владельцу кода приходит 🟡 3, а когда друг
дорастёт до 10 уровня — ещё 🟡 5. Свой код вписать нельзя, обменяться кодами
друг с другом — тоже.

## Логи по HTTP

Приложение отдаёт свой лог-файл наружу: `GET /logs?tail=500` целиком и
`GET /logs/stream` живым потоком (SSE), оба с необязательным `&grep=...`.

Доступ закрыт паролем `ADMIN_PASSWORD` — тем же, что у админ-панели. Пароль
передаётся заголовком или query-параметром:

```bash
curl -H "Authorization: Bearer $ADMIN_PASSWORD" https://<домен>/logs?tail=500
curl "https://<домен>/logs?tail=500&key=$ADMIN_PASSWORD"
```

Без пароля (и если `ADMIN_PASSWORD` не задан) оба роута отвечают 404. В логах
лежат peer_id игроков, тексты их сообщений и номера заказов доната со суммами —
поэтому открытыми их держать нельзя.

## Long Poll — второй путь сообщений от ВК

Сообщения игроков ВК присылает по Callback API — и порой задерживает их на
минуты. Бот может параллельно забирать их сам, по Bots Long Poll API: какое из
двух пришло первым, то и ложится в очередь, а копия отбрасывается (см.
«Очередь входящих событий ВК»). Callback остаётся включённым — на нём держатся
билеты активности. Где Long Poll остановился, хранится в `vk_longpoll`: после
перезапуска он продолжает с того же места и сразу забирает пришедшее за паузу.

Включить:

1. «Управление сообществом» → «Работа с API» → «Long Poll API»: Long Poll API —
   «Включён», версия API — 5.199; в «Типах событий» — «Входящее сообщение».
2. В `.env` — `VK_LONG_POLL=true`, затем `docker compose up -d`.
3. В логе бота — `Long Poll: слушаю ВК`. Если вместо этого раз в минуту
   `Long Poll: ВК не дал подключиться` — Long Poll в сообществе выключен или у
   ключа доступа сообщества нет права «Управление сообществом».

Какой путь быстрее, видно на дашборде: «Доставка от ВК по путям» — опоздание
каждого, «Откуда взято событие» — каким путём сообщения приходили первыми.
Выключить — `VK_LONG_POLL=false`.

## Гильдейское сообщество — беседы гильдий

Второе сообщество ВК — только для бесед: гильдии и прочие общие беседы зовут
его к себе, и там работают те же команды, что в общей и торговой, — «Передать»,
«Мой профиль», «Моё снаряжение», «Туториал», «Дать»; ответ — от его имени.
Основное сообщество слушает только общую и торговую беседы
(`VK_CHAT_PEER_ID`, `VK_TRADE_CHAT_PEER_ID`). В личку гильдейского бот отвечает
одной строкой: играть — в основном.

Номера бесед у сообществ свои и совпадают (у каждого первая — 2000000001),
поэтому беседа для бота — номер вместе с сообществом: ответ — токеном её
сообщества, ключи повторов у гильдейского свои, кнопки «Приложение» и
«Туториал» — только в общей и торговой основного. Событие гильдейского ложится
в `vk_inbox` завёрнутым — `{"guilds": событие}`: прежняя версия бота его не
разберёт и в чужую беседу не ответит.

Гильдейское сообщество слушается только по Long Poll — Callback у него не
настраивается. Где Long Poll остановился, хранится второй строкой
`vk_longpoll` (`id = 2`).

Включить:

1. В сообществе, «Управление» → «Работа с API»: ключ доступа с правами
   «Сообщения сообщества» и «Управление сообществом»; «Long Poll API» —
   «Включён», версия API — 5.199, в «Типах событий» — «Входящее сообщение».
   «Сообщения» → «Настройки для бота»: возможности ботов включены, добавлять
   сообщество в беседы разрешено.
2. В `.env` — `VK_TOKEN_FOR_GROUP_CHATS=<ключ>`: он нужен и боту (отвечать), и
   сборщику (слушать).
3. Выложить бота, затем сборщика (см. «Обновление»):
   `scripts/deploy-bot.sh`, затем `docker compose up -d --no-deps collector`.
4. В логе сборщика — `Long Poll гильдейского сообщества: слушаю ВК`.
5. В каждой беседе дать сообществу доступ ко всей переписке: иначе ВК присылает
   ему только сообщения с упоминанием.

Выключить — убрать `VK_TOKEN_FOR_GROUP_CHATS` из `.env` и пересоздать сборщика.
Откатить бота, пока сборщик слушает гильдейское сообщество, можно: события в
обёртке прежняя версия не разберёт — они уйдут в `Failed`, ничего не сделав.

## VK Mini App — инвентарь и аукцион

Приложение в `web/`: сумка, снаряжение и аукцион, с поиском, фильтрами по типу
и монете и сортировкой. Описание вещи — тот же текст, что в карточке бота. Пока
только просмотр, поэтому смотреть можно откуда угодно, даже из боя: сцены и лок
игрока приложение не трогает.

Данные отдаёт бот: `GET /api/app/inventory` и `GET /api/app/auction`. Игрока он
узнаёт по параметрам запуска, которые ВК подписывает защищённым ключом
приложения, — приложение шлёт их в заголовке `X-Launch-Params`. Параметры
годятся сутки, потом приложение просит открыть его заново. Героя приложение не
заводит: игру начинают в сообщениях сообщества.

Включить:

1. Создать в ВК мини-приложение и вписать его «Защищённый ключ» в `.env` как
   `VK_APP_SECRET`. Пока ключа нет, `/api/app/...` отвечает 404.
2. Вписать в `.env` адрес сервера: `DOMAIN=<имя>` — имя, которое уже указывает
   на IP сервера. Затем `docker compose up -d --build --no-deps caddy`: контейнер `caddy`
   соберёт приложение из `web/`, сам получит сертификат Let's Encrypt и начнёт
   отдавать по `https://<имя>/` приложение, а `/api`, `/pay` и `/logs` — пересылать
   боту. Получилось ли — в `docker compose logs caddy` («certificate obtained»).
3. В настройках приложения ВК во всех адресах (vk.com, мобильная версия,
   мобильные клиенты) указать `https://<имя>/`.

`DOMAIN` обязателен: без него `caddy` не запускается, а он теперь принимает и
колбэк ВК, и вебхук кассы (см. «Роли: сборщик и бот»). Сертификат Caddy
получает через порт 443 (TLS-ALPN). Касса может слать вебхук и на
`https://<имя>/pay/tbank/notify`.

Локально, без ВК:

```bash
export VK_APP_SECRET=dev-secret
sbt app/run                                # бот на :8080
cd web && npm install && npm run dev       # приложение на :5173, /api — на бота
npm run sign -- dev-secret <vk_id игрока>  # адрес, открывающий приложение от его имени
```

## Очередь входящих событий ВК

Callback и Long Poll ход не играют — они кладут событие в таблицу `vk_inbox` и
только потом отвечают ВК «ok». Не легло (база недоступна) — ВК получает 500 и
повторит событие сам, так что принятое не теряется и при падении бота. Повторы —
то же сообщение другим путём или повтор Callback — отсекает ключ `dedup_key`.

Разбирает очередь `InboxWorker`: опрос раз в 100 мс, захват через
`FOR UPDATE SKIP LOCKED` с арендой 5 секунд, каждое событие — своим фоновым
делом, без ограничения числа. У каждого игрока берётся только его самое раннее
ждущее событие — ходы идут по порядку и при нескольких ботах. Сломалось — повтор,
после трёх попыток `Failed`, и очередь игрока идёт дальше. Обработанные события
хранятся неделю (пароль админ-панели в них замаскирован). На дашборде —
«Очередь ВК»: сколько ждёт, сколько ждало и сколько упало.

## Бэкапы базы

Каждый день в 3:00 (МСК — время сервера) cron запускает `scripts/backup-db.sh`:
дамп базы (`pg_dump -Fc`, без данных служебных `vk_inbox` и `vk_seen_messages`), проверка,
что архив читается, и копия на Google Drive в папку `pangea-backups`. Там
хранятся копии за 30 дней, на сервере — 3 последние (`/root/backups/pangea`).
Дамп снимается внутри работающего контейнера postgres: бот не останавливается и
не перезапускается. Не вышло — сообщество пишет в ВК всем из
`BACKUP_ALERT_VK_IDS`. Журнал — `/var/log/pangea-backup.log`.

rclone ходит в Google Drive с доступом «только свои файлы» (`scope = drive.file`):
остальное содержимое Диска ему не видно. Удалённые копии Google держит в
корзине ещё 30 дней.

Настроить один раз:

1. На сервере: `apt install rclone`.
2. На своём компьютере (там, где есть браузер): `brew install rclone`, затем
   `rclone authorize "drive" "eyJzY29wZSI6ImRyaXZlLmZpbGUifQ"` (это
   `{"scope":"drive.file"}`) — откроется Google, войти и разрешить. В терминале
   появится строка между `--->` и `<---End paste` — скопировать её.
3. На сервере: `rclone config` → `n` → имя `gdrive` → тип `drive` →
   `client_id` и `client_secret` пустые → `scope` — `drive.file` → прочее по
   умолчанию → `Use web browser...?` — `n` → вставить строку из шага 2 → `y`.
   Проверка: `rclone about gdrive:` показывает место на Диске.
4. В `.env`: `BACKUP_ALERT_VK_IDS=<id>,<id>`.
5. Первый запуск руками: `scripts/backup-db.sh` — в конце «готово: pangea_….dump».
   Проверить сообщение о сбое: `BACKUP_REMOTE=nope: scripts/backup-db.sh`.
6. Включить расписание: `cp scripts/pangea-backup.cron /etc/cron.d/pangea-backup`.

Восстановление — только руками и при остановленном боте:

```bash
rclone copy gdrive:pangea-backups/pangea_<дата>.dump /root/backups/restore/
docker compose stop app
docker compose exec -T postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists --no-owner' \
  < /root/backups/restore/pangea_<дата>.dump
docker compose start app
```

Проверить копию, не трогая игру, — восстановить её в отдельную базу:

```bash
docker compose exec -T postgres sh -c 'createdb -U "$POSTGRES_USER" restore_test'
docker compose exec -T postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d restore_test --no-owner' \
  < /root/backups/restore/pangea_<дата>.dump
docker compose exec -T postgres sh -c 'dropdb -U "$POSTGRES_USER" restore_test'
```

## Метрики и графики

Бот пишет метрики (`pangea.metrics.GameMetrics`): время ходов и где ход ждёт —
доставка от ВК, лок игрока, API ВК, пул базы; самые медленные сцены; опоздание
таймеров; ошибки; память, GC и потоки JVM. Prometheus собирает их каждые 15
секунд и хранит 30 дней, Grafana показывает дашборд «Пангея» — по нему можно
задним числом посмотреть, что было с ботом в любую минуту.

Всё поднимается тем же `docker compose up -d --build`. Метрики приложение
отдаёт на внутреннем порту 9464 — наружу он не открыт. Grafana — на
`http://<IP сервера>:3000`, вход `admin` / `GRAFANA_PASSWORD` из `.env`; без
пароля она не запускается (порт открыт наружу). Пароль Grafana берёт из `.env`
только при самом первом запуске — сменить его потом:

```bash
docker compose exec grafana grafana cli admin reset-admin-password '<новый пароль>'
```

Дашборд лежит в `docker/grafana/dashboards/pangea.json`: правки в интерфейсе
при перезапуске Grafana перезапишутся файлом, постоянные — коммитом в него.

Дашборд «Донат» (`docker/grafana/dashboards/donations.json`) берёт данные не
из Prometheus, а прямо из базы — таблицы `payments`: суммы точные, история
целиком. Grafana ходит туда под ролью `pangea_grafana`, которую создаёт
миграция: только чтение и только нужные колонки (почты для чека она не видит).
Пароль роли задаётся один раз — на сервере, в каталоге проекта:

```bash
docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
# в psql: \password pangea_grafana — и тот же пароль в .env как GRAFANA_DB_PASSWORD
docker compose up -d --no-deps grafana
```
